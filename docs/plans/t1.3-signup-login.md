## Goal

The first real endpoints:
- a visitor signs up, which creates their account, an organization and their Admin membership, and signs them in
- a user logs in and out
- `/me` lists the caller's active memberships
- a signed-in user creates another organization

Login and signup are rate-limited, and login answers the same way whether or not the email exists. T1.3 also brings
the trusted organization scope that T1.2's hand-off found missing, moved here from T1.5. The organization context
middleware itself stays in T1.5.

## What exists (checked 2026-10-25)

- **Current user.**
  - `HttpCurrentUser` reads `UserId` and `OrganizationId` from the claims and is registered as the scoped
    `ICurrentUser`.
  - Nothing adds the organization claim before T1.5 (P14), so no request has an organization context yet.
- **Interceptors.**
  - `OrganizationOwnershipInterceptor` throws when an organization-owned row is saved without an organization context,
    so signup's membership can't be saved without a trusted scope.
  - `AuditInterceptor` stamps `CreatedBy` from `ICurrentUser.UserId`: null at signup (user, organization, membership),
    and the caller at `POST /organizations`.
- **One context, one transaction.** `IFixFlowDbContext` resolves to the same scoped `FixFlowDbContext` as Identity's
  `UserStore`, so one `Database.BeginTransactionAsync` covers the save inside `UserManager.CreateAsync`. In an
  explicit transaction, post-commit events wait for the commit.
- **Unique violations.**
  - `WriteAsync` translates only concurrency conflicts (P11). A unique violation surfaces as a `DbUpdateException`
    around a `PostgresException` `23505`, which `DatabaseAssertions.AssertUniqueViolationAsync` checks.
  - Application can't see Npgsql, so a handler can't map that exception to a field.
  - `ix_users_normalized_email` is named in `UserConfiguration`; `ix_organizations_slug` comes from the snake_case
    convention.
- **Query filters.** They are named (`QueryFilters.Organization`, `QueryFilters.SoftDelete`), so
  `IgnoreQueryFilters([QueryFilters.Organization])` keeps the soft-delete filter.
- **Model test gap.** `DbContextInterface_ExposesOnlyScopedSets` checks only the element type of each `IQueryable`. A
  query of an organization-owned type that ignores the organization filter would pass it.
- **Results.** `ResultExtensions` has `ToOk` and `ToNoContent`, but nothing for 201.
- **T1.2's test endpoints.** `IdentityTestEndpoints` has:
  - `/sign-in`, kept "until T1.3 adds signup and login"
  - `/session`, which returns the principal's claim values (the S26 check)

  `UserAccountTests` use its password constant.
- **Endpoints.**
  - `Program.cs` holds a placeholder for the first endpoint modules.
  - No endpoint names its OpenAPI operation, so orval would name hooks after the path (`usePostApiV1AuthSignup`).
- **SPA.** `web/src/api/http.ts` redirects every 401 to `/login`, except on `/login` itself.
- **Identity facts** (release/10.0 sources):
  - `UserManager.CreateAsync` runs the password and user validators (`DuplicateEmail`), then saves.
  - `UserStore.CreateAsync` doesn't catch `DbUpdateException`, so a lost race comes out of `CreateAsync` as an
    exception.
  - The description of `DuplicateEmail` contains the address, so only error **codes** may be logged or mapped.
- **Records.** A record's generated `ToString` prints every property, including a password.
- **To verify early:** TestServer leaves `HttpContext.Connection.RemoteIpAddress` null. If it does, a per-IP limiter
  would put all parallel tests in one partition.

## Decisions (confirmed 2026-10-25)

★ = recommended · ✔ = chosen. The options are kept so a later change of mind starts from them.

### D1 — The trusted organization scope

| | Option | For | Against |
|---|---|---|---|
| **A ✔★** | **An override inside `ICurrentUser`.** `ITrustedOrganizationScope.Open(organizationId)` (Application) returns an `IDisposable`. A separate scoped `TrustedOrganizationScope` (API) implements it, and `HttpCurrentUser` reads its open id, so casting `ICurrentUser` doesn't reach it. While the scope is open, `ICurrentUser.OrganizationId` returns that id, so the interceptor, the filters and the audit stamps work unchanged. The scope stays open through the commit, so post-commit handlers run in it too. `Open` throws when a context already exists. An architecture test allow-lists the types that may use it. | CLAUDE.md §3.1 still holds: the id reaches persistence only through `ICurrentUser`, and the server derived it. No entity-specific rule in the interceptor. T3.2's invite acceptance reuses it. | Any handler that gets the interface could open a scope for any id, which is why the allow-list test exists. |
| B | A founding rule in the interceptor: `OrganizationMembership.Create(organizationId, …)`, and the interceptor accepts an added membership whose organization is added in the same save. | No new service. | An entity-specific exception in a safety net. Invite acceptance (an existing organization) still needs a scope later. |
| C | Pull T1.5's middleware and claims transformation forward. | One design for every context. | T1.5 is L. Signup has no header to resolve, so it would still need a special case. |

Record as **P25**.

### D2 — What a failed login answers

| | Option | For | Against |
|---|---|---|---|
| **A ✔★** | **422 with one fixed detail** for a wrong password, an unknown email and a locked-out account. The detail is not a field error. | Reuses `Result.Unprocessable` and fits mvp.md's status table. It never triggers the SPA's 401 → `/login` redirect, which matters on T3.4's invite page, where an existing user signs in. | Less common than 401 for a login endpoint. |
| B | 401. | The common REST answer. | Needs a new `ErrorType`. The SPA's redirect would have to skip every page with a login form. |
| C | 400. | | Shares a status with validation errors. |

The locked-out case gets the same answer, or a lockout would tell an attacker that the account exists. The fixed
detail says both things, e.g. "The email or password is incorrect, or the account is locked for a while after too
many failed attempts."

### D3 — Session lifetime (left open by T1.2)

| | Option | For | Against |
|---|---|---|---|
| **A ✔★** | **`rememberMe` on login.** True gives a persistent cookie (Identity's 14 days, sliding); false gives a session cookie. Signup signs in with a session cookie. | The usual UX, and safe on shared computers. One bool. | One more field in the login form (T1.7). |
| B | Always persistent. | The simplest. | A shared computer stays signed in until logout. |
| C | Session cookies only. | The most conservative. | More logins on phones. |

### D4 — Which endpoints are rate-limited (S6)

| | Option | For | Against |
|---|---|---|---|
| **A ✔★** | **Login and signup**, with one `auth` policy, a budget per endpoint and client IP, and limits from configuration. T1.4 adds forgot and reset password to it. | Signup is also an email-enumeration oracle (a taken email gives a 422) and a way to spam organizations. | Stricter than S6's wording, so ARCHITECTURE §15 and S6 get "signup". |
| B | Login only. | Exactly S6. | Signup stays open until T9.3. |

D2–D4 are recorded as **P26** (auth flow) and **P28** (rate limiting).

### Settled by existing rules, with no question needed

- **The auth flow uses MediatR handlers, plus a session port.**
  - Endpoints stay thin (`src/CLAUDE.md` §2), and `SignInManager` stays in API (P22).
  - Application gets `IAuthSession` (password sign-in with lockout, sign-in, sign-out), implemented in API with
    `SignInManager<User>`. Handlers use `UserManager<User>` directly (P22).
  - Part of **P26**.
- **Unique violations get an Application exception**, the way concurrency does (P11).
  - `WriteAsync` turns `23505` into `UniqueConstraintViolationException(constraintName)`.
  - Handlers map their own constraints to `Result.FieldError`; anything else stays a 500 (a bug).
  - The constraint names become Application constants (`UniqueIndexes`), and the configurations use them.
  - Recorded as **P27**.
- **The signup unit of work** follows T1.2's hand-off, with two changes:
  - The organization and the membership go in **one** save. The organization's id exists before the insert (D10), so
    the scope can open before anything is saved.
  - The scope covers the whole unit of work, commit included. `DomainEventsTransactionInterceptor` dispatches the
    post-commit events at the commit, so a scope that closed earlier would leave signup's post-commit handlers without
    the organization context that those of `POST /organizations` get.

  Steps:
  1. `Organization.Create`, then open the scope for its id
  2. begin the transaction
  3. `UserManager.CreateAsync`. Inside the scope this is harmless: users aren't organization-owned, and the audit stamps
     read only `UserId`.
  4. `OrganizationCreator` adds the organization and the membership, then saves
  5. commit; the post-commit events run here, still inside the scope
  6. close the scope, then sign in

  `POST /organizations` takes the same steps without 2, 3 and 6. Its single save dispatches the post-commit events
  inside the scope too.
- **Responses.**

  | Endpoint | Success | Errors |
  |---|---|---|
  | `POST /auth/signup` | 201, the new organization `{ id, name, slug }`, so the SPA can go to `/{slug}` | 400, 422, 429 |
  | `POST /auth/login` | 204 | 400, 422, 429 |
  | `POST /auth/logout` | 204 | 401 |
  | `GET /me` | 200 | 401 |
  | `POST /organizations` | 201, the new organization | 400, 401, 422 |

  - After a login the SPA reads `/me`.
  - The 201s carry no `Location`, because organizations have no GET endpoint yet.
- **Logout needs a session.**
  - S7's anonymous allow-list stays at signup and login.
  - A cross-site POST carries no `SameSite=Lax` cookie, so it gets a 401 and can't sign anyone out.
  - An expired session gets a 401, and the SPA goes to `/login`, which is where logout leads anyway.
  - Logout removes the cookie from this browser only. Cookie auth keeps no server-side session, so a copy of the
    cookie stays valid until it expires or the security stamp changes (T1.4).
- **Login CSRF.**
  - Minimal APIs bind bodies from `application/json` only, so an HTML form posted from another site gets 415 (A11).
  - A test pins it.
- **Unknown email.** The handler hashes the given password anyway (`UserManager.PasswordHasher`), so most of the
  timing difference goes away. A known email still costs one more database write; that is accepted.
- **Validation (400) and conflicts (422).** The validators mirror the domain rules, so `DomainException` stays a
  backstop:

  | Field | Rule |
  |---|---|
  | email | ≤ 256 characters (Identity's column), FluentValidation's `EmailAddress` (the same check as Identity's) |
  | password | 10–128 characters; `PasswordPolicy.MaxLength = 128` is new |
  | names | ≤ 100 characters, no control characters |
  | organization name | `Organization`'s rules |
  | slug | `OrganizationSlug.IsValid`, with its message |

  - Login validates only that the fields are present and within the maximum lengths.
  - The validators check trimmed values: FluentValidation's `Transform(..., v => v?.Trim())` on the email, the names
    and the organization name. Handlers trim the email too, so a stray space can't make a second account, and what
    passes validation is what gets stored.
  - The slug is taken as written (P21): whitespace fails `OrganizationSlug.IsValid`, which gives a 400.
  - The duplicate email and the taken slug are 422s.
- **The body's field names:**
  - signup: `email`, `password`, `firstName`, `lastName`, `organizationName`, `slug`
  - `POST /organizations`: `name`, `slug`

  `ix_organizations_slug` maps to `slug` in both, and `ix_users_normalized_email` to `email`.
- **Signup needs an anonymous caller.** Otherwise `AuditInterceptor` would stamp the signed-in user A as `CreatedBy`
  on B's account, organization and membership. A signed-in caller gets a 422 ("You're already signed in…"), and
  creates an organization with `POST /organizations` instead. The endpoint stays `AllowAnonymous`; the handler checks
  `ICurrentUser.UserId`.
- **Logs carry ids only.** Identity errors are logged by code. Commands that carry a password override
  `PrintMembers`, so a logged command never prints it (S26).
- **`/me` reads through two scoped queries** on `IFixFlowDbContext` (P22: "scoped reads, each with a reason"):
  - `OwnAccount`: the caller's user row.
  - `OwnMemberships`: the caller's memberships in every organization. It is the one place that turns off the
    organization filter, with its justification, and T1.5's membership resolution reuses it.
- **Rate limiting.**
  - Built-in fixed window with no queue, partitioned by (route pattern, client address); 10 requests a minute by
    default, from `RateLimiting:Auth`.
  - The client address is the IPv4 address (an IPv4-mapped IPv6 address counts as IPv4), or the **/64 prefix** of an
    IPv6 address. A client usually controls a whole /64, and would otherwise get a fresh budget from each address.
  - A rejected request gets a 429 Problem Details with `Retry-After`.
  - Tests give every client its own /64 from the documentation prefix `2001:db8::/32` (D23), so parallel tests never
    share a budget.
- **Operation names.** These are the first real endpoints, so each sets `WithName` (`SignUp`, `LogIn`, `LogOut`,
  `GetMe`, `CreateOrganization`). orval then generates `useGetMe` rather than `useGetApiV1Me`. This is a new, small
  convention: noted in `src/CLAUDE.md` §2.

## Steps

### Session 1 — trusted scope, unique violations, own-account queries

- [x] **Trusted organization scope** (D1):
  - `Application/Auth/ITrustedOrganizationScope.cs`: `IDisposable Open(Guid organizationId)`. Its XML docs say:
    - it's only for an id the server derived itself, such as the organization it just created or an invite's
      organization, never one from the request
    - the caller has no organization context
  - `TrustedOrganizationScope` (API, `Auth/`, internal, scoped) implements it:
    - it holds the open id
    - `Open` throws `InvalidOperationException` for `Guid.Empty`, when a scope is already open, or when the request's
      principal already has an organization claim (read through `IHttpContextAccessor`)
    - disposing closes the scope, and a second dispose does nothing
  - `HttpCurrentUser` takes `TrustedOrganizationScope` (the concrete type) and reads `OrganizationId` as the open
    scope's id, else the claim. It doesn't implement `ITrustedOrganizationScope`, so casting `ICurrentUser` can't open a
    scope.
  - Docs: `ICurrentUser`'s summary, and `OrganizationMembership.Create`'s "(T1.5)" → T1.3.
  - Tests:
    - In API.IntegrationTests, plain unit tests over a `DefaultHttpContext`: open → `HttpCurrentUser` shows the id;
      dispose → it's gone; open with an organization claim → throws; open inside an open scope → throws.
    - In API.IntegrationTests' `ArchitectureTests`, `TrustedOrganizationScope_UsedOnlyByAllowListedTypes`: constructor
      parameters across Application, Infrastructure and API. The list is `SignUpHandler` and
      `CreateOrganizationHandler`; T3.2 adds `AcceptInviteHandler`. `HttpCurrentUser` takes the concrete type and isn't
      on the list. The test lives in the API test project because it's the only one that sees all three assemblies.
- [x] **Unique violations** (P27):
  - `Application/Errors/UniqueConstraintViolationException.cs` has `ConstraintName` and implements `ILogSafeMessage`.
    Its message is built from the constraint name only.
  - `Application/Persistence/UniqueIndexes.cs`: `UserEmail`, `OrganizationSlug` and `MembershipUserOrganization`,
    holding today's names. The three configurations name their unique indexes with these (`HasDatabaseName`), so
    there's no migration, which `Migrations_CoverTheModel` confirms.
  - `FixFlowDbContext.WriteAsync`: a second `catch` for
    `DbUpdateException { InnerException: PostgresException { SqlState: PostgresErrorCodes.UniqueViolation } }`. It
    goes **after** the concurrency `catch`, because `DbUpdateConcurrencyException` derives from `DbUpdateException`.
  - Tests:
    - `DatabaseAssertions.AssertUniqueViolationAsync` expects the new exception and its `ConstraintName`; its three
      callers stay as they are.
    - `ConcurrencyTests` and `UpdateUser_Concurrently_ReturnsConcurrencyFailure` stay green unchanged.
- [x] **Own-account queries** (`IFixFlowDbContext`, implemented in `FixFlowDbContext`):
  - `IQueryable<User> OwnAccount`: `Users.Where(u => u.Id == CurrentUserId)`, a private property like
    `CurrentOrganizationId`, so EF Core turns it into a parameter. Anonymous callers get no rows.
  - `IQueryable<OrganizationMembership> OwnMemberships`:
    `OrganizationMemberships.IgnoreQueryFilters([QueryFilters.Organization]).Where(m => m.UserId == CurrentUserId)`.
    The justifying comment says that a user's own memberships decide which organizations they may enter, so they're
    read before any organization context exists (`/me`, T1.5).
  - `DbContextInterface_ExposesOnlyScopedSets`: every `IQueryable` property that isn't a `DbSet` must be on a named
    allow-list with its reason (`OwnAccount`, `OwnMemberships`). This closes the element-type-only gap.
  - Persistence tests (`Persistence/OwnAccountQueryTests.cs`, on `api.Persistence`):
    - two users in one organization each see only their own membership
    - a member of A and B sees both without an organization context, and with A's context too
    - an anonymous caller sees neither
    - `OwnAccount` returns the caller's row only
- [x] **`OrganizationCreator`** (`Application/Organizations/`, internal, scoped, registered in `AddFixFlowApplication`):
  - `CreateAsync(Organization organization, Guid founderId, CancellationToken)` → `Result`. It runs inside the trusted

    `ICurrentUser.OrganizationId` is anything else. It doesn't open the scope itself, so the scope can stay open

    1. add the organization and `OrganizationMembership.Create(founderId, [Role.Admin], clock.GetCurrentInstant())`
    2. save once
  - A `UniqueConstraintViolationException` on `UniqueIndexes.OrganizationSlug` becomes
    `Result.FieldError("slug", "This slug is already taken.")`. Anything else propagates.
- [x] **`IAuthSession`** (`Application/Identity/IAuthSession.cs`), implemented by `Auth/SignInManagerAuthSession.cs`

### Session 3 — rate limiting, contract, docs, verification

- [x] **`AddFixFlowRateLimiting()`** (no configuration parameter, see "Found while implementing") (API, `RateLimiting/RateLimitingExtensions.cs`):
  - `AuthRateLimitOptions`, from the `RateLimiting:Auth` section:
    - `PermitLimit` = 10 and `Window` = 1 minute
    - data annotations with `ValidateOnStart`
    - the defaults mean the build-time OpenAPI run needs no setting
  - Policy `RateLimitPolicies.Auth`: a fixed window with no queue, partitioned by the endpoint's route pattern and

## Found while implementing

### Session 1 (2026-10-25)

- **The tests can't see internal types.** No project has `InternalsVisibleTo`, so a test can't construct
  `TrustedOrganizationScope`, `HttpCurrentUser` or `OrganizationCreator`.
  - `Auth/TrustedOrganizationScopeTests` builds `AddFixFlowAuth()` in its own `ServiceCollection` and resolves the two
    interfaces. Its `IHttpContextAccessor` is a stub that holds one `DefaultHttpContext`, because the framework's
    accessor keeps the context in a static `AsyncLocal`. This also checks the registrations: the handler and the
    current user share one scope object per request.
  - The tests also cover the empty id, a second dispose after the scope was opened again (it doesn't close the new
    one), another request (it sees no organization), and casting `ICurrentUser` to the scope interface (not possible).
  - `OrganizationCreator` has no test of its own. Session 2's signup and `POST /organizations` tests reach it,
    including the taken slug.
- **`OrganizationFounder.FoundAsync` was renamed** `OrganizationCreator.CreateAsync` after Session 1, on request. The
  steps above use the new names.
- **The allow-list test differs from the plan in three ways.**
  - It names types by their full name, because handlers are `internal`. The two handler names don't exist until
    Session 2, so until then they match nothing.
  - It flags any constructor parameter assignable to `ITrustedOrganizationScope`, so the concrete class counts too:
    otherwise an API type could take the class and open a scope unnoticed. `HttpCurrentUser` is therefore **on** the
    list, as the one type that takes the class (to read the open id). The plan said it wouldn't be.
  - It skips types nested in a scope implementation: the scope's private `Closer` takes the class to close it, and the
    first run flagged it.
- **The unique-violation catch also requires a constraint name** (`ConstraintName: { }`). PostgreSQL always names
  the index of a unique violation. One without a name would stay a `DbUpdateException`, which gives a 500.
- **The slug and membership indexes had their names from the snake_case convention.** They now get the same names
  explicitly from `UniqueIndexes`, and `Migrations_CoverTheModel` confirms there's no migration.
- **`OwnAccountQueryTests`' anonymous case** opens the organization context, as signup does. In that context the
  organization filter alone would let the rows through, so only the user predicate keeps them out.
- **`ToCreated` has no test of its own.** Session 2's 201 tests (`SignUp_Valid_…`,
  `CreateOrganization_SignedIn_…`) should also assert that the response has no `Location` header.
- **`SignInOutcome`** is in its own file, next to `IAuthSession`.

### Session 2 (2026-10-25)

- **FluentValidation 12 has no `Transform`** (removed in 12.0). The validators check trimmed values with

  a line break, so `Email()` adds `NoControlCharacters()`. Without it, `"us\ner@x"` would pass validation, then fail

### Session 3 (2026-10-26)

- **TestServer leaves `RemoteIpAddress` null**, as suspected. A throwaway test showed it first.

  window on a rejected lease. That's an upper bound on the wait, so the header stays correct, and the test checks a
  range (1 s to the window).

  `RateLimitingExtensions.ClientAddressKey` are `public`, because the tests can't see internals (Session 1). A null

## Watch out for

- **Catch order in `WriteAsync`:** keep the concurrency catch first. The unique catch filters on `SqlState`, but a
  reordering would still read wrongly.
- **A failed save ends the unit of work.** After a unique violation the handler returns its 422 and saves nothing
  more. Disposing the transaction rolls back, and the context drops the pending post-commit events.
- **Lockout uses Identity's clock** (T1.2). Lockout expiry stays untested; starting the lockout is tested.
- **Timing:** hashing on an unknown email hides most of the difference, not all of it. A locked-out account answers
  without hashing (Identity's pre-check). Both are accepted.
- **Secure cookie in Vite dev** (T1.2): there's no UI before T1.7, so check it there in Chromium and Firefox.
- **`IgnoreQueryFilters` takes names.** Calling it without arguments would also drop soft delete. `OwnMemberships` is
  the only call site, and it names `QueryFilters.Organization`.
- **Signup reveals that an email has an account**, which self-signup with globally unique emails (D5) can't avoid. The
  rate limit slows it down.
- **The lockout can be used as a denial of service.** S3 requires a per-account lockout (5 attempts, 15 minutes).
  Anyone who knows an email can keep that account locked, and the per-IP limit doesn't stop an attacker with many
  addresses. This is accepted for the MVP: revisit it in T9.3, and with MFA in Phase 2. It's listed under mvp.md's
  "Gaps noted".
- **A copied cookie outlives logout** until it expires or the security stamp changes (T1.4).
- **Resolving `ITrustedOrganizationScope` from `IServiceProvider`** would bypass the allow-list test, which only sees
  constructor and method parameters (an endpoint delegate's too). Handlers never resolve services that way; a code
  review catches it.
- **The scope stays open through the commit.** Closing it before the commit would run signup's post-commit handlers
  without an organization context (see "Settled → signup unit of work").

## Review (2026-10-25)

A `/code-review` of this plan returned 10 findings.

Folded in:
1. **The scope's lifetime was ambiguous.** The founder's steps opened the scope to add the membership and then
   listed the save as a separate step, so a literal implementation would save outside the scope and throw. The scope
   now spans the whole unit of work.
2. **Signup's post-commit handlers ran without an organization context**, because the commit came after the scope had
   closed, while those of `POST /organizations` ran inside it. The handlers now open the scope, and it closes after the
   commit.
3. **"The same body" can't hold:** each Problem Details carries its own `traceId`. The test compares fields instead.
4. **A signed-in signup credited the wrong user** in `CreatedBy`. Signup now needs an anonymous caller.
5. **Casting `ICurrentUser` reached the scope**, and the allow-list test checked only Application. The scope is now a
   separate class, and the test checks Application, Infrastructure and API.
6. **An IPv6 client could rotate addresses** inside its /64. The partition key now uses the /64 prefix.
7. **The lockout as denial of service** was neither accepted nor mitigated. It's accepted and documented.
8. **Validators checked untrimmed values.** They check the trimmed ones now. The finding's "500" was wrong:
   `DomainException` maps to 422.
9. **Logout's limits were implicit.** A copied cookie stays valid, and the plan now says so.

Kept:
10. **`/me` takes two queries.** Both are indexed lookups and read more simply than one projection with a nested
    collection; `/me` isn't hot enough to need one query.
