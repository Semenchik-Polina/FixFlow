# T1.6 Authorization framework — Implementation plan

**Status:** done 2026-10-31 (Sessions 1–3; review pending) · **Size:** M (≈ 3 sessions) · **Branch:** `feat/t1.6-authorization`, stacked on
`feat/t1.5-organization-context` until T1.5 is merged into `dev`
**Scope and DoD:** `docs/plans/mvp.md` T1.6. This file only says how. Tick T1.6 there when done.

## Context

T1.5 gave every org request an `OrganizationId` and the caller's roles (`ICurrentUser.Roles`, `fixflow:role` identity).
Nothing uses the roles yet: every endpoint is either anonymous or "authenticated" (fallback policy). T1.6 adds the two
authorization layers of §8 so that T2.2 onward can guard endpoints and records:

1. **Endpoint layer:** named role policies over the active org's roles (403 when the role is missing).
2. **Record layer:** operation-based checks inside handlers (404 when not allowed) + the `VisibleTo(user)` list
   convention.
3. **Safety net (S7):** a coverage test that fails when an endpoint has no explicit policy, an unlisted
   `AllowAnonymous`, or an org endpoint without a role policy.

## Decisions

**Confirmed with the user (2026-10-31):**
- **Record checks are in-house, over `ICurrentUser`** — not ASP.NET Core's `IAuthorizationService`. Application keeps
  no `Microsoft.AspNetCore.*` reference (T1.5's architecture test stays as is) and handlers never need a
  `ClaimsPrincipal`. §8 item 2 and `src/CLAUDE.md` §5 get reworded; recorded as **P34**. D7 is unchanged → no ADR.
- **Catalog = the six policies named in the scope.** Later slices add theirs (each with a row in the matrix test).

**Settled by existing rules (no question needed):**
- **Role policies read `ICurrentUser.Roles`, not `RequireRole`.** CLAUDE.md §3.1: roles come only from `ICurrentUser`.
  One custom requirement + handler; no policy sets `AuthenticationSchemes` (T1.5 hand-off).
- **Admin is listed explicitly** in every Manager policy (`Role.cs`: "the policies grant it that").
- **No org context ⇒ every role policy fails (403)**, so a role policy on an org-less endpoint fails closed.
- **`HttpCurrentUser` reads the org id and roles only from the org-context identity.** Found while planning:
  `IdsOnlyClaimsPrincipalFactory` passes stored user claims (`AspNetUserClaims`) into the cookie identity, and
  `FindFirst`/`FindAll` search every identity, cookie first. A stored `fixflow:role` / `fixflow:organization_id` row
  would grant a role in every org. Nothing writes such rows, but roles now gate endpoints, so close it.
- **Detail reads load through `VisibleTo(user)`**, so "View" and the list can't disagree; the per-resource
  authorization handler covers the other operations on a loaded record. Unknown operation → denied.

## Steps

### Session 1: role policies

1. **`src/FixFlow.API/Auth/Policies.cs`** — `public static class Policies`: one `const string` per policy (its own
   name) and an internal `FrozenDictionary<string, Role[]>` table (the catalog above), the single place roles per
   policy are written.
2. **`OrganizationRoleRequirement`** (`IAuthorizationRequirement`, holds the role set) and
   **`OrganizationRoleHandler(ICurrentUser)`** (`AuthorizationHandler<OrganizationRoleRequirement>`, scoped): succeeds
   iff `OrganizationId is not null && Roles.Overlaps(requirement.Roles)`. Verify early that a scoped handler resolves
   per request (it should: the policy evaluator comes from request services).
3. **Registration** in `AuthExtensions.AddFixFlowAuth` (`src/FixFlow.API/Auth/AuthExtensions.cs:60-62`): extend the
   existing `AddAuthorizationBuilder()` with one `AddPolicy` per table row
   (`RequireAuthenticatedUser().AddRequirements(...)`); comment that no policy sets `AuthenticationSchemes`.
4. **Hardening `HttpCurrentUser`** (`src/FixFlow.API/Auth/HttpCurrentUser.cs`): move the middleware's
   `AuthenticationType = "FixFlow.Organization"` (`OrganizationContextMiddleware.cs:35`) to `OrganizationContext` as a
   public const; `OrganizationId` and `FindRoles` read only the identity with that authentication type. `UserId` still
   reads the cookie identity. The trusted-scope branch is unchanged.
5. **OpenAPI 403:** a `RolePolicyResponsesTransformer` next to `OrganizationContextResponsesTransformer`
   (`src/FixFlow.API/OpenApi/`) adds a 403 Problem response to operations whose `IAuthorizeData.Policy` is in the
   catalog. Extract the "register ProblemDetails component + `TryAdd` problem response" code both share into one
   internal helper. Register it in `OpenApiExtensions`.
6. **Tests:**
   - Fixture: make `OrganizationWithEveryRoleAsync` (`tests/.../Fixtures/CrossTenantExtensions.cs:74`) public, so a
     test needs one org, not two.
   - Test module `tests/.../Auth/PolicyTestEndpoints.cs` (`/api/v1/test-policies`, registered in `FixFlowApiFactory`
     like the other test modules): `GET /{policy}` → 204 for every catalog policy (requires an org, the default), plus
     one org-less endpoint with `CanManageOrganization` to prove it fails closed.
   - `tests/.../Auth/RolePolicyTests.cs`:
     - Theory per policy with a **hand-written** expected role set (independent of `Policies`): one org, each of the
       four role clients → 204 or 403 (403 read with `ReadProblemAsync(HttpStatusCode.Forbidden)`, no redirect).
     - The expected table's keys equal the catalog's (a new policy needs its row).
     - **DoD:** `MemberOfBothAsync(A, [Manager], B, [Tenant])` → `CanManageProperties` with `b` → 403, with `a` → 204;
       `CanSubmitRequests` the other way round (positive control).
     - A member with Technician + Tenant passes both `CanWorkOnJobs` and `CanSubmitRequests`, fails `CanManageProperties`.
     - Anonymous → 401; foreign slug → 404 (the middleware answers before the policy).
     - A role change through `ChangeMembershipAsync` (Manager → Tenant) → 403 on the next request.
     - The org-less endpoint with a role policy → 403 for the org's Admin.
   - `HttpCurrentUserTests`: a cookie identity carrying `fixflow:role` / `fixflow:organization_id` claims gives no
     roles and no org; the org identity still does.
   - `OpenApiDocumentTests`: the test module's operation has 403; `/me` and `GET /test-organization/context` don't.

### Session 2: coverage test + record-level pattern

1. **Coverage test.** Rename `tests/.../Conventions/OrganizationContextCoverageTests.cs` → `EndpointCoverageTests.cs`
   (its doc comment already says T1.6 extends it). Move the checks into pure functions over `IEnumerable<Endpoint>`
   that return violations, so the same checks run on the host and on synthetic endpoints. Host-wide checks (all
   endpoints, test modules excluded), keeping T1.5's two org checks:
   - **Anonymous allow-list:** the endpoints with `IAllowAnonymous` are exactly signup, login, forgot-password,
     reset-password, `/health/live`, `/health/ready` and the SPA fallback (pattern from `SpaExtensions.ClientRoutePattern`).
   - **Explicit authorization:** every endpoint has `IAllowAnonymous` or at least one `IAuthorizeData`, never both;
     the fallback policy alone doesn't count (S7).
   - **Org endpoints name a role policy:** every endpoint that requires an org has an `IAuthorizeData.Policy` from the
     catalog; plain `.RequireAuthorization()` isn't enough there.
   - **Org-less endpoints use no role policy** (it would always 403).
   - **No `AuthenticationSchemes` or `Roles`** on any endpoint's `IAuthorizeData`, and none on any catalog policy
     (`IAuthorizationPolicyProvider.GetPolicyAsync`).
   - **Negative controls (the DoD's "fails for…"):** synthetic `RouteEndpointBuilder` endpoints — one with no
     authorization, one with an unlisted `AllowAnonymous`, one org endpoint with only `.RequireAuthorization()`, one
     with `AuthenticationSchemes` — each reported by its check.
2. **Record-level pattern** in `src/FixFlow.Application/Auth/`:
   - `Operation.cs`: `public sealed record Operation(string Name)` (`ToString` = name, for logs). Modules define
     `WorkOrderOps.Assign = new("WorkOrder.Assign")` etc.
   - `IResourceAuthorizationHandler<TResource>`:
     `ValueTask<bool> IsAllowedAsync(TResource resource, Operation operation, CancellationToken ct)`. Implementations
     take `ICurrentUser` (and `IFixFlowDbContext` when they need a lookup, e.g. a tenant's units) and deny operations
     they don't know.
   - `IResourceAuthorizer` + internal `ResourceAuthorizer(IServiceProvider, ICurrentUser, ILogger)`:
     `IsAllowedAsync<TResource>(resource, operation, ct)`. No org context or no roles (also a trusted scope) → false
     without calling the handler; no handler registered for `TResource` → `InvalidOperationException` (a bug, so a
     500 in tests, never a silent 404); a denial logs at Debug with the operation, resource type and user id (S26).
   - `ServiceCollectionExtensions.AddFixFlowApplication`: register `IResourceAuthorizer` (scoped) and scan the
     assembly for `IResourceAuthorizationHandler<>` implementations, the way `AddDomainEventHandlers` does
     (`src/FixFlow.Application/ServiceCollectionExtensions.cs:44`). Expose the scan as
     `AddResourceAuthorizationHandlers(assembly)` so tests can register theirs.
   - **`VisibleTo` is a convention, not code, until T4.3:** `<Entity>QueryExtensions.VisibleTo(this IQueryable<T>,
     ICurrentUser)`, a `switch` on roles that ends in `Where(_ => false)`; detail reads go through it too.
3. **Application tests** `tests/FixFlow.Application.Tests/Auth/ResourceAuthorizerTests.cs`, with a test resource, a
   test handler and a fake `ICurrentUser` in a `ServiceCollection`: allowed → true; unknown operation → false; no org
   context / trusted scope (org, no roles) → false and the handler isn't called; no handler → throws; the scan
   registers the handler. Add `Microsoft.Extensions.DependencyInjection` / logging abstractions to the test project
   only if they don't come transitively.

## Found while implementing

### Sessions 1–3 (2026-10-31)

- **`FrozenSet<Role>` takes collection expressions**, so the catalog in `Policies` reads as the table above. It is
  public: the test module maps one endpoint per key, and `RolePolicyTests` checks its keys against its own table.
- **The scoped `OrganizationRoleHandler` resolves per request** (the "verify early" point): the policy evaluator comes
  from the request's services, and `RolePolicyTests` shows each request getting its own organization's roles.
- **The OpenAPI transformers share `ProblemResponses.TryAddAsync`**, moved out of
  `OrganizationContextResponsesTransformer`. `openapi.json` is unchanged: no shipped endpoint has a role policy yet.
- **`ResourceAuthorizer` insists on exactly one handler per resource**, not only on one being there. It resolves them
  all: a second registration (a factory, say) would otherwise win silently. The handler is looked up before the
  organization check, so a resource without one fails on every call, not only on the calls that reach it.
- **The assembly scan is shared** with the domain event handlers (`Implementations` in `ServiceCollectionExtensions`).
- **The anonymous check is "every anonymous endpoint is on the list"**, not equality. The SPA fallback is mapped only
  where the SPA's `index.html` exists, which the shared test host doesn't have, so its pattern is on the list as text
  (`ClientRouteConstraint` is internal). `AnonymousEndpoints_AreAllowListed` asserts that login is among the anonymous
  endpoints, so the check reads real metadata.
- **"Explicit authorization" also reports an endpoint that is anonymous and authorized at once**: `AllowAnonymous` wins
  silently. An inline `AuthorizationPolicy` counts as none: endpoints name a policy.
- **Negative control by hand:** without `.RequireAuthorization()` on `GET /me`, `Endpoints_DeclareTheirAuthorization`
  failed with `["GET /api/v1/me"]`; restored.
- **Docker Desktop wasn't running** at first; the integration tests need it (Testcontainers).
- **`TrustedOrganizationScope.Open` still refuses on an organization claim anywhere in the principal**, a stricter
  check than `HttpCurrentUser`'s, so it fails closed. `Open_RequestHasOrganizationClaim_Throws` built its claim on an
  identity of type `Test`, which the current user now ignores; it builds the organization context's identity instead.
- **Tests added:** 8 `ResourceAuthorizerTests`; 13 `RolePolicyTests`, 2 `HttpCurrentUserTests`, 1 OpenAPI test and 14
  coverage tests (16 in `EndpointCoverageTests` with T1.5's two). The whole solution passed after a `--no-incremental`
  build with no warnings: 82 domain, 157 application and 370 integration tests. `openapi.json` was unchanged, so there
  was no `gen:api` run.
