## Context

T1.3 shipped signup, login, logout and `/me`. T1.4 lets a user who forgot their password get it back by email, and lets
a signed-in user change their password and name. It also brings the first real email sender (P7: the interface has
existed since T0.7, but nothing implements it), and it fixes a review finding on `dev` (2026-10-21): health-check
settings are read eagerly, so `Program.cs` needs `BuildTimeDocument.IsGenerating` guards.

## Decisions (confirmed 2026-10-26)

| # | Decision | Why |
|---|---|---|
| D1 | **Stamp validated on every request** (`SecurityStampValidatorOptions.ValidationInterval = TimeSpan.Zero`). A reset or a change ends every other session on its next request. | Matches T1.5's "suspension takes effect on the very next request". No time travel needed. Cost: one user lookup per signed-in request (the review removed the re-issued cookie: Review #3). |
| D2 | **Our own reset-token provider on `IClock`**: `PasswordResetTokenProvider : IUserTwoFactorTokenProvider<User>` (API/Auth). It mirrors `DataProtectorTokenProvider`: a Data Protection payload of the created `Instant`, the user id, the purpose and the security stamp, encoded as base64url. Valid while `now < created + 1 h` (`ResetPasswordCode.Lifespan`, a constant the email states too, S4). | FakeClock tests pin the boundary, like T3.1's invites. CLAUDE.md §3.4 (time through `IClock`). |
| D3 | **Forgot-password sends inline and catches every failure.** A new port, `IExceptionRedactor.ForLog(Exception)` (Application/Errors), is implemented in Infrastructure with `RedactedException`. The dispatcher switches to it, with the same output. | No schema change. ADR 0007's formatting reaches a second call site. |
| D4 | **The SMTP failure tests use Mailpit Testcontainers** from compose's tag (P6): `Mailpit` (normal) and `RejectingMailpit` (`MP_CHAOS_TRIGGERS=Recipient:550:100`; chaos is global per instance), plus a closed port for "down". | A real server. Chaos replies don't quote the address, so a test of the translation function covers that case. |

### Settled by existing rules (no question needed)

- **Single use.** `ResetPasswordAsync` changes the security stamp, so the token stops matching. A race between two
  resets with one token hits Identity's `ConcurrencyFailure` and gets the **same 422**, so exactly one wins. A reset or
  a change also voids every other outstanding token.
- **The link is built from configuration, never from the request's `Host`** (that's how password-reset poisoning
  works).
  - `ISpaLinks.ResetPassword(code)` (Application) is implemented by `Spa/SpaLinks` (API) from `Spa:PublicUrl`.
  - The link is `{PublicUrl}/reset-password#token={code}`: the token travels in the fragment (A11).
  - `/reset-password` is already a reserved slug (P21).
- **The token is one opaque value.** `ResetPasswordCode` (Application) gives `"{userId:N}.{providerToken}"`, which is
  URL-safe. The body is `{ token, newPassword }`, so the SPA never handles an email address. A malformed code, an
  unknown user, an expired, used or foreign token, or a lost race all get **one 422**, with no field:
  "This reset link is invalid or has expired. Ask for a new one."
- **A successful reset ends the lockout.** It clears `LockoutEnd` and `AccessFailedCount` on the user before
  `ResetPasswordAsync`, so its one save carries them, and an invalid token saves nothing. The owner proved control of
  the inbox, and this softens the lockout-DoS gap from T1.3.
- **A reset doesn't sign anyone in.** It returns 204, and the SPA goes to `/login`.
- **Forgot-password always answers 202**, apart from a malformed email (400, which reveals nothing) and 429. An unknown
  email logs `Password reset requested for an unknown email` and sends nothing. The known-email path is slower by one
  SMTP round trip: that's accepted, because signup already reveals whether an account exists (T1.3), and the endpoint
  is rate-limited.
- **Changing the password counts toward the lockout.** `IAuthSession.CheckPasswordAsync(user, password)` uses T1.3's
  row-locked transaction and `CheckPasswordSignInAsync(…, lockoutOnFailure: true)`, then `ChangePasswordAsync`.
  - A wrong password, or a locked-out account → 422 field error on `currentPassword`: "The current password is
    incorrect, or the account is locked for a while after too many failed attempts."
  - Success → `IAuthSession.RefreshSignInAsync(user)` (new), so this browser keeps its session (and its
    `isPersistent`) while the others end (D1).
  - It takes credentials, so it's rate-limited (`src/CLAUDE.md` §2).
- **Changing the name** goes through `UserManager.UpdateAsync`, not `OwnAccount` plus a save, because P11 leaves raw EF
  conflicts for users. `ConcurrencyFailure` → `ConcurrencyConflictException` (409). It isn't rate-limited.
- **Settings without a safe default validate on first use** (`ValidateDataAnnotations()`, no `ValidateOnStart`):
  `SmtpOptions` and `SpaLinkOptions`. So the build-time run needs no settings. Settings with defaults (rate limits)
  keep `ValidateOnStart`. The health checks take `Func<IServiceProvider, string>`.
- **Email templates are C#, with no library.** `Application/Email/EmailLayout` builds the text and HTML bodies and
  HTML-encodes every value. Each email has a factory next to its use case. The strings live in that one class (D27).
- **`EmailMessage` overrides `PrintMembers`** to print the subject only. The address and bodies (with the token) never
  reach a log (S26).
- **`EmailDeliveryException : Exception, ILogSafeMessage`** (Application/Email):
  - `Kind` (`Connect`, `Tls`, `Authentication`, `Command`, `Protocol`, `Timeout`), with `SmtpStatus` (int?) and
    `SmtpErrorCode` (string?) when the server answered.
  - Its message is built from these fields only, e.g. `"SMTP command failed: 550 MailboxUnavailable
    (RecipientNotAccepted)."`. The original is the inner exception.
  - `SmtpCommandException.Message` and `.Mailbox` are never read.
- **Responses:**

  | Endpoint | Operation | Success | Errors | Auth |
  |---|---|---|---|---|
  | `POST /auth/forgot-password` `{ email }` | `ForgotPassword` | 202 | 400, 429 | anonymous, rate-limited |
  | `POST /auth/reset-password` `{ token, newPassword }` | `ResetPassword` | 204 | 400, 422, 429 | anonymous, rate-limited |
  | `POST /me/password` `{ currentPassword, newPassword }` | `ChangePassword` | 204 | 400, 401, 404, 409, 422, 429 | signed in, rate-limited |
  | `PUT /me/name` `{ firstName, lastName }` | `ChangeName` | 204 | 400, 401, 404, 409 | signed in |

  Every endpoint is organization-less (`/auth/*`, `/me*`), so T1.5's middleware must leave them alone.

- **P30:** the MailKit sender and `EmailDeliveryException`, C# templates, links from `Spa:PublicUrl`, and D3

## Found while implementing

### Session 1 (2026-10-26)

- **The NpgSql health check needs no data source of our own.** `AddNpgSql`'s `connectionStringFactory` overload
  (AspNetCore.HealthChecks.NpgSql 9.0.0) builds its `NpgsqlDataSource` once, on the first probe. Checked with a probe
  app: three checks, one factory call, one data source.
- **The Dockerfile's `design-time-placeholder` stays.** `dotnet ef migrations bundle` without `Database:Password`
  (user-secrets hidden) fails while it creates the DbContext and writes no bundle. The comment now says the DbContext
  needs the password, not Program.
- **Hosts without the API lost the dispatcher.** `PersistenceTestDatabase` and `ModelConventionTests` call
  `AddFixFlowPersistence` on their own, and the dispatcher's new `IExceptionRedactor` didn't resolve there (the old
  `IOptions<ExceptionLoggingOptions>` always did), so the whole integration run failed in the assembly fixture.
  `AddFixFlowPersistence` now `TryAdd`s the redactor, which removes messages (the old default).
  `AddFixFlowExceptionLogging` `TryAdd`s it too, so the call order doesn't matter.
- **New package `Microsoft.Extensions.Options.DataAnnotations`** (10.0.13, the `Microsoft.Extensions.Options` version
  EF Core brings). Infrastructure has no ASP.NET Core framework reference, so `ValidateDataAnnotations()` for
  `SmtpOptions` wasn't available. It's Microsoft's own glue for the pattern the plan names, but CLAUDE.md §4 asks before
  new packages, so it's flagged here.
- **`EmailDeliveryException` also has `SmtpStatusName`.** The plan's example message names the status ("550
  MailboxUnavailable"), and Application can't get that name from 550 without MailKit. It's null for a code MailKit
  doesn't name, and the message is then `SMTP command failed: 599 (UnexpectedStatusCode).`
- **MailKit's own timeouts.** `MailKitEmailSender` turns an `OperationCanceledException` that isn't the caller's into
  `Timeout`. `MailKitFailures` leaves every cancellation alone, as planned.
- **Mailpit chaos.** On v1.31.6, `MP_CHAOS_TRIGGERS` alone turns chaos on (`/api/v1/chaos` reports the trigger), so
  `MP_ENABLE_CHAOS` isn't needed.
- **Shapes Session 2 builds on:**
  - `ISpaLinks` is in `Application/Email` and returns a `Uri`.
  - `EmailLayout` is a builder: `new EmailLayout().Paragraph(text).Link(label, uri).ToMessage(to, subject)`. `Link`
    throws for anything but an absolute http(s) URL.
  - In tests: `FixFlowApiFactory.SpaPublicUrl` (`https://fixflow.example.test`), and the Mailpit handles
    `api.MailpitSmtp`, `api.RejectingSmtp` and `api.Mailpit` (`SingleToAsync(recipient)`, `HeaderAsync`).
- **Gitleaks and test tokens.** The pre-commit hook blocked a made-up random-looking code after `#token=` in
  `SpaLinksTests` (`generic-api-key`: a token keyword plus a value with entropy over 3.5). In tests, write token-like literals as
  readable, low-entropy values (`user-id.reset_code`), or build them at run time, rather than allow-listing them.
- **Tests beyond the plan:**
  - `Hosting/SpaLinksTests`: the path is kept, the token is in the fragment, and an invalid `Spa:PublicUrl` fails on
    first use.
  - A `MailKitFailuresTests` theory over each transport failure.

### Session 2 (2026-10-27)

- **D1 re-issues the cookie on refused requests too.** Every signed-in response now carries the session's own cookie,
  re-issued, whatever the status. Two T1.3 tests asserted "no auth cookie" on a signed-in client's refused request to
  mean "no new session" (`LogIn_FormPost_IsRefusedBeforeTheEndpoint`, `SignUp_WhileSignedIn_Returns422`). They now
  assert that the client is still signed in as itself. If the re-issue is ever trimmed ("Watch out for": D1's cost),
  the old check would hold again.
- **CA1822 on an empty `PrintMembers`.** A command that prints nothing has a `PrintMembers` that reads no instance
  data, and the analyzer wants it static, which a record's can't be. Each of the four commands suppresses it with a
  justification, as `IInTransactionEventHandler` does for CA1711.
- **`IdentityResultExtensions`** (Application/Identity, internal): `HasError(code)`, `ThrowIfFailed(action)`
  (`ConcurrencyFailure` → `ConcurrencyConflictException`, anything else → `InvalidOperationException` with the codes)
  and `Unexpected(action)`. Reset, change password and change name share it; signup keeps its own checks.
- **The reset sets the lockout fields on the entity.** `SetLockoutEndDateAsync` and `ResetAccessFailedCountAsync` each
  save, so the handler sets `LockoutEnd` and `AccessFailedCount` itself, and `ResetPasswordAsync`'s one save carries
  them.
- **Changing the password hashes the current one twice:** the check that counts towards the lockout, then
  `ChangePasswordAsync`'s own. Identity has no public way to set the hash without either a second check or a second
  save, and this keeps one save. The second check runs against the hash just checked, so it can't disagree.
- **A reset by a signed-in caller stamps them as `UpdatedBy`.** The audit interceptor credits the request's user, so
  resetting another account's password with its link while signed in records the caller on that account. Signup

- **The provider stores the creation time in ticks** (`Instant.ToUnixTimeTicks`). That's finer than any test needs:
  `JustBeforeOneHour` advances by the lifespan minus `Duration.Epsilon`.

## Watch out for

- **D1's cost.** Every signed-in request loads the user to compare the stamps. A matching stamp re-issues nothing
  (`NonRenewingSecurityStampValidator`, Review #3). That's fine at MVP scale; revisit in Phase 2 if it shows up.
- **Sliding renewal still re-issues the cookie**, with the principal the request started with. So Review #3's race is
  still possible on that one request, about once a week for an active session. If a user is signed out right after
  changing their password, this is why.
- **The security stamp validator tracks the `User`** early in each request, so handlers get that instance back from
  `FindByIdAsync`. `SignInManagerAuthSession` reloads it under its row lock, as before.
- **`IssuedUtc` is stored to the second.** An interval of zero still validates on every request, because the elapsed
  time is always greater than zero.
- **A misconfigured SMTP setting shows up at the first send**, as an `OptionsValidationException` (redacted to its type
  outside Development), and forgot-password still returns 202. Check the manual run's logs.
- **Don't bridge cookies to the `FakeClock`.** Only the reset token reads `IClock`; lockout and cookie expiry stay on
  the system clock (as in T1.3).
- **Chaos is global per Mailpit instance.** Only `RejectingMailpit` has triggers; never set chaos on `Mailpit` from a
  test.
- **The reset link's fragment.** T1.7 must remove it from the history (`replaceState`) once it has read it.
