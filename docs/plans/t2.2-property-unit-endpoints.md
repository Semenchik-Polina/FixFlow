**Scope and DoD:** `docs/plans/mvp.md` T2.2. This file only says how. Tick T2.2 there when done.

## Context

T2.1 added the `Property` and `Unit` aggregates, their mapping and migration, with no endpoints. T2.2 exposes them to
Managers and Admins: properties (list paged + name filter, get, create, update, archive) and a property's units (list,
create, update, archive). T2.3's UI is built on the generated client this slice produces. These are the first
organization-scoped business endpoints, so this slice also adds the first `VisibleTo`, the first resource authorization
handlers and the first 201 that comes with a `Location`.

## Decisions

**Confirmed with the user (2026-11-03):**
- **Archiving a property archives its active units too**, in one save, using one `IClock` instant. T4.3 later adds
  "open requests → 422" before that runs. Recorded as **P38** in `mvp.md`.

**My calls (following existing rules):**
- **Routes** (all `.RequireAuthorization(Policies.CanManageProperties)`, one module `PropertyEndpoints`, prefix `/properties`):

  | Verb + path | Name | Success |
  |---|---|---|
  | `GET ""` `?page&pageSize&name` | `ListProperties` | 200 `PagedResult<PropertyResponse>` |
  | `GET /{id:guid}` | `GetProperty` | 200 `PropertyResponse` |
  | `POST ""` | `CreateProperty` | 201 + `Location: /api/v1/properties/{id}` |
  | `PUT /{id:guid}` | `UpdateProperty` | 204 |
  | `POST /{id:guid}/archive` | `ArchiveProperty` | 204 |
  | `GET /{propertyId:guid}/units` `?page&pageSize` | `ListUnits` | 200 `PagedResult<UnitResponse>` |
  | `POST /{propertyId:guid}/units` | `CreateUnit` | 201, no `Location` (no unit GET) |
  | `PUT /{propertyId:guid}/units/{unitId:guid}` | `RenameUnit` | 204 |
  | `POST /{propertyId:guid}/units/{unitId:guid}/archive` | `ArchiveUnit` | 204 |

  Archive is an action `POST`, like T4.3's `/cancel` and T3.2's revoke, not `DELETE`. Updates answer 204, like
  `PUT /me/name`; the SPA invalidates its queries.
- **Ids come from the route only.** Bodies carry fields; the endpoint builds the command with the route ids.
  Create and update share one body per resource (`PropertyRequest`, `UnitRequest`), so T2.3's create/edit dialog has
  one type. (Changed while building: the plan had create bind its command directly.)
- **JSON shape:** `{ id, name, address: { line1, line2, city, postalCode, countryCode }, timeZone }` in both requests
  and responses. The domain's `TimeZoneId` is `timeZone` on the wire, so field errors use `timeZone` and
  `address.line1`, … (`FieldNames` already camelCases dotted paths). Unit: `{ id, propertyId, name }`.
- **Unit list is paged too** (§15, "always paginate lists"), ordered by name. The property list is ordered by name,
  then id (names aren't unique). The name filter is trimmed, matches a case-insensitive substring in SQL, and a blank
  filter means no filter. It is limited to `Property.NameMaxLength`.
- **`VisibleTo`:** Manager/Admin → everything in the org, anyone else → `Where(_ => false)`. Later slices add the
  tenant (its units) and technician (its jobs' properties) cases.
- **Resource checks:** `PropertyOps` (`Property.Update`, `Property.Archive`, `Property.AddUnit`) and `UnitOps`
  (`Unit.Rename`, `Unit.Archive`). One handler per resource lets Manager/Admin do every known operation and denies
  anything else. Create property has no record, so its role policy is the only check.
- **Unit routes check the property first:** it must be visible (`IFixFlowDbContext.Units` says filters don't look at
  the property), and the unit must belong to it. A unit id under the wrong property gives 404.
- **Domain:** `Property.Update(name, address, timeZoneId)`, which shares Create's checks, and `Unit.Rename(name)`. No
  row version (T2.1: §10 limits xmin to WO/MR), so concurrent edits are last-write-wins. No domain events.
- **Unit name taken** (create or rename) → catch `UniqueConstraintViolationException` for `UniqueIndexes.UnitName` →
  `Result.FieldError("name", "A unit with this name already exists in this property.")` → 422 (P27).
- **Personal data (S24/S26):** the address-carrying commands and `PropertyAddress` print no members (`ChangeNameCommand`'s
  `PrintMembers => false`). Logs carry ids only.
- **Skipped (not asked):** unarchive, `includeArchived`, unit GET, sort params, caching, row versions.

### Found while building

- `Npgsql` translates `ToUpper()` (→ `upper()`) and `Contains` (→ `strpos`, so `%` and `_` match literally), not
  `ToUpperInvariant()` or the `StringComparison` overloads. The filter is `NameContains` in `ListPropertiesHandler`, with
  justified `SuppressMessage`s for CA1304/CA1311/CA1862; the term is uppercased in .NET.
- `OpenApiDocumentTests.Document_Numbers_AreJsonNumbersOnly` took `.Single()` paged schema; the first real paged lists
  made three. It now checks every `PagedResultOf*` schema.
- `PropertyAddress`'s `line2` and `postalCode` are required-but-nullable in the OpenAPI document (positional record):
  the SPA sends `null` for a missing one.
- The role policy is on the group (`group.RequireAuthorization(Policies.CanManageProperties)`); `EndpointCoverageTests`
  reads it from every endpoint's metadata.

## Accepted risks

- Last-write-wins on concurrent edits (no row version on these aggregates).
- A unit created while its property is being archived can survive as active. The nested routes can't reach it, because
  they load the property first. T4.3's open-request check doesn't change this.
