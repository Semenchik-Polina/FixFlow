# T1.2 Identity & account persistence — Implementation plan

**Status:** done 2026-10-23; D3 changed from B to A on 2026-10-25 · **Size:** M (≈ 3 sessions) · **Branch:** `feat/t1.2-identity-persistence` off `dev`
**Scope and DoD:** `docs/plans/mvp.md` T1.2. This file only says how. Tick T1.2 there when done.
**Reviewed:** with `/code-review` (2026-10-23). All 9 findings are folded in below.

## Goal

ASP.NET Core Identity and the organization tables are persisted with the first migration, `AddIdentityAndOrganizations`.
Users can be created and signed in with an S1 cookie, and the model tests make organization isolation the default for
every future entity. T1.2 adds no endpoints: T1.3 adds signup and login on top of this.

## What exists (checked 2026-10-23)

- T1.1 domain: `Organization` (global, slug rules), `OrganizationMembership` (`IOrganizationOwned`, `IAuditable`, a
  `_roles` backing field), `MembershipRole` (no id), and the enums `Role` and `MembershipStatus`.
- T0.9 persistence:
  - `FixFlowDbContext : DbContext` applies its conventions to root, non-owned entity types.
  - `SaveChanges` (synchronous) throws on purpose, because domain events need the async save.
  - `WriteAsync` turns every `DbUpdateConcurrencyException` into `ConcurrencyConflictException` (P11), and a failed
    save blocks later saves in the scope.
  - `Schemas.Identity` and `Schemas.Organizations` exist. **There are no migrations yet.**
  - The test model is created with `EnsureCreated` from `TestDbContext`, so it gets the app's entities too.
- T0.8 auth: `AddIdentityCookies()` with 401/403 events and the fallback policy. The application cookie's
  `OnValidatePrincipal` already calls `SecurityStampValidator`, but nothing registers one yet. That is harmless only
  while no cookie exists.
- The test factory starts the host (`StartServer()`) **before** it applies the migrations
  (`FixFlowApiFactory.InitializeAsync`).
- Checked facts, in release/10.0 sources:
  - `IdentityUserContext` maps schema Version 1 unless `Stores.SchemaVersion` ≥ 3, so there is no passkeys table.
  - Identity's `EmailIndex` is **not unique**. ARCHITECTURE §10's "(Identity default)" is wrong.
  - Identity names its indexes explicitly (`UserNameIndex`, `EmailIndex`), so the snake_case model test fails on them
    until they're renamed.
  - `UserClaimsPrincipalFactory` puts `UserName` into `ClaimTypes.Name`.
  - `UserStore.UpdateAsync` reports a concurrency conflict only by catching `DbUpdateConcurrencyException`.
  - `UserStore` saves the whole context on every `CreateAsync` and `UpdateAsync` (`AutoSaveChanges`).
  - `UserManager` reads the system clock for lockout, not `IClock`.
  - `SecurityStampValidator` compares stamps only after its `ValidationInterval` (30 minutes by default) has passed.
  - `EntityFrameworkCoreXmlRepository.StoreElement` saves keys with the **synchronous** `SaveChanges()`. This matters
    only for D3-B.
  - In a container, the default key folder logs "may not be persisted outside of the container", even with a volume
    mounted there.

## Decisions (confirmed 2026-10-23; D3 changed 2026-10-25)

★ = recommended · ✔ = chosen. The options are kept so a later change of mind starts from them.

### D1 — Where `User` lives, and how handlers read users

| | Option | For | Against |
|---|---|---|---|
| **A ✔★** | **`User : IdentityUser<Guid>` in Application** (`FixFlow.Application/Identity/User.cs`, from `Microsoft.Extensions.Identity.Stores`, with no ASP.NET Core dependency). **`IFixFlowDbContext` has no unfiltered `Users`.** Later slices add scoped reads, each with a reason: the user's own row (T1.3 `/me`), and the organization's users through the org-filtered memberships (T3.3). A test checks the interface's shape. The Identity setup (stores, options, EF mapping) is in Infrastructure; `SignInManager` is in API. | Handlers project names with LINQ (P13). Application handlers can use `UserManager<User>` (Microsoft.Extensions.Identity.Core). Isolation comes from the interface's shape, not a written rule (R1). | Identity's fields (`PasswordHash`, …) are visible in handler code, so projections must leave them out. Each scoped read needs care. |
| B | `User` in Infrastructure, with ports in Application: `IUserAccounts` (passwords, names) and `IUserDirectory` (DTO reads). | Application never sees Identity types. | Every read of user names goes through a hand-written port, which works against P13. Joins with organization data are split across layers. |
| C | A `UserProfile : Entity` in Domain (id, names) and Identity's `User` in Infrastructure (credentials, email). Either one table by EF table splitting, or two tables with Identity's left untouched. Credential operations go through a port. | No credentials in Application, and the profile is a real domain entity. | `Entity` needs a constructor that takes an id. Table splitting has rules, or two tables need a join. A credentials port (T1.3/T1.4). An email in member lists needs a column mapped in both types, or the port. |

Record as **P22**, together with D4.

### D2 — Password policy (S3)

| | Option | For | Against |
|---|---|---|---|
| **A ✔★** | **At least 10 characters, with no composition rules** (`RequireDigit/Lowercase/Uppercase/NonAlphanumeric = false`, `RequiredUniqueChars = 1`). | Exactly what S3 says, and in line with NIST SP 800-63B. T1.3's validator rule is one line. C can be added later with no migration. | `aaaaaaaaaa` is accepted. |
| B | At least 10, plus Identity's defaults (a digit, a lower- and an uppercase letter, a symbol). | Nothing to configure except the length. | Four rules S3 doesn't ask for, which NIST advises against. The SPA has to mirror five rules. Worse UX. |
| C | At least 10, plus a custom `IPasswordValidator<User>`: no email local part or name inside, and not on an embedded list of common passwords. | The strongest option without composition rules. | More code. The list's licence needs checking, and the list sits in a public repo. The SPA can't mirror the check. |

### D3 — Data Protection key storage (the keys that protect the auth cookie)

| | Option | For | Against |
|---|---|---|---|
| **A ✔★** | **A configured folder** (`DataProtection:KeysPath` → `PersistKeysToFileSystem`), with the named volume `api-data-protection` mounted there in the `full` profile. Unset (the API on the host, tests), the framework's default folder applies. | The smallest change: no package, table or second DbContext. The container warning goes away. Phase 2's replicas on one host share the volume. | Works on one machine only, because a named volume lives on one Docker host. **History:** B was chosen on 2026-10-23 and implemented. On 2026-10-25 it was replaced by A, the smaller change.
Moving to B later, with hosting, means:
- adding the package, the table and the small context
- registering `PersistKeysToDbContext`
- users sign in once more, unless the key files are copied into the table

Every option sets `SetApplicationName("FixFlow")`, so all instances share the key ring. Keys stay unencrypted at rest
in the container (the "No XML encryptor configured" warning), which is accepted while everything runs locally; revisit

### D4 — What `UserName` holds

| | Option | For | Against |
|---|---|---|---|
| **A ✔★** | **The user's id** (`Id.ToString()`). Login: `FindByEmailAsync`, then `PasswordSignInAsync(user, …, lockoutOnFailure: true)`. `RequireUniqueEmail = true`, plus the unique email index. | No email in `ClaimTypes.Name`, claims or logs (S26). Identity's default username check stays on. Any email address works. A later email change touches only `Email`. | Less common than username = email. The unique username index is redundant. Code must use the `User` overloads, never the by-name ones. |
| B | The email, with the RFC 5322 local-part characters added to Identity's set. | The usual Identity setup. The username check stays on. | The email is in `ClaimTypes.Name`, a log risk. Non-ASCII addresses are rejected. An email change updates two fields. |
| C | The email, with the character check off (`AllowedUserNameCharacters = ""`). | Accepts every address. | Any path that skips the validator can store any username (the review finding). The email is in the claims, as in B. |

### Settled by existing rules, with no question needed

- **Enums are stored as text**, by convention in `ConfigureConventions`. §10's partial index (`WHERE status <> 'Cancelled'`)
  already assumes it, and a reordered enum can't corrupt data. Record it as **P23** and in `src/CLAUDE.md` §4.
- **`IdentityUserContext<User, Guid>`, not `IdentityDbContext`.** Roles belong to memberships (D7), so there are no
  Identity role tables.
- **Concurrency on users stays Identity's business.** `WriteAsync` passes a `DbUpdateConcurrencyException` through
  untouched when every conflicting entry is a `User`, so `UserStore` can return `ConcurrencyFailure`. Every other
  conflict still becomes `ConcurrencyConflictException` (P11). Note this in P11's row.
- **Lockout:** 5 attempts, 15 minutes, `AllowedForNewUsers = true`. `RequireConfirmedEmail = false` (P3).
- **Cookie:** `HttpOnly`, `SecurePolicy = Always`, `SameSite = Lax`. Expiry stays at Identity's default (14 days,
  sliding); T1.3 decides between persistent and session cookies.
- **Foreign keys** from memberships to `organizations` and to `users` use `Restrict` (deleting users or organizations
  is out of MVP). Roles cascade with their membership, as owned rows do.
- **`User` is `IAuditable`.** `CreatedBy` is null at signup. `UpdatedAt` also moves on Identity's own updates
  (lockout counter, security stamp), which is fine.
- **Identity store options stay at their defaults** (`SchemaVersion`, `MaxLengthForKeys`, `ProtectPersonalData`). The
  test persistence has no `IdentityOptions`, so any non-default value would give the app model and the test model
  different shapes.

## Found while implementing (2026-10-23)

- **NuGet audit (D3-B only):** the NuGet package `Microsoft.AspNetCore.DataProtection` 10.0.12 pulls
  `System.Security.Cryptography.Xml`/`.Pkcs` 10.0.12, which have advisories (CVE-2026-84008, -96960, -70162) fixed in
  10.0.13. While B was in place, both were pinned to 10.0.13. A uses the shared framework's Data Protection, so the
  package and the pins went with B. Whoever brings B back needs the pins again, unless the packages are on 10.0.13+ by
  then.
- **T0.9's convention loop kept orphaned types.** It called `builder.Entity(type)` on every root type. That made
  Identity's passkey data, behind a passkey set that schema Version 1 ignores, explicit, so EF couldn't drop it ("needs
  a primary key"). Each convention now calls `Entity(type)` only when it applies.
- **Foreign key names went stale.** The snake_case plugin names a foreign key from its principal's table name *at
  that moment*, and configurations are applied alphabetically. The FKs to users were therefore named
  `…_asp_net_users_…`.
  - Fix: `FixFlowDbContext` applies `UserConfiguration` before the rest.
  - New model test: `ForeignKeyNames_NameTheirTables`. Plain snake_case can't catch this, since `asp_net_users` is
    valid snake_case.
- **Naming:** `FixFlowIdentityExtensions`, because `IdentityServiceCollectionExtensions` clashes with Microsoft's
  class. The test endpoint is `/session`, not `/me`.
- **Already covered:** T0.8's `Get_EndpointNotAllowListedAnonymously_Returns401WithoutRedirect` already asserted that
  there's no `Location` header, so it needed no change.
- **Migration checklist:** Identity's `user_claims` has an `int` identity key.
- **`/code-review` of the implementation (2026-10-23)**, 10 findings. Fixed:
  - Identity's principal factory also adds the **email as a claim**, so D4 alone didn't keep the email out of the
    principal. `IdsOnlyClaimsPrincipalFactory` removes it, and `SignedIn_Principal_CarriesNoEmail` checks it.
  - The convention marker list duplicated `ApplyConventions`. Each convention now calls `Entity(type)` itself, only
    when it applies.
  - `User`'s docs say to create accounts only with `UserManager.CreateAsync`. A direct insert, a seed say, gets no
    normalized email (so it slips past the unique index) and no lockout.
  - mvp.md's DoD rule 5 got `--context`. It was dropped again when D3 went to A on 2026-10-25: one context needs none.
- **Kept as they are:**
  - After an Identity `ConcurrencyFailure`, the scope can't save again. That's the existing "a failed save ends the
    unit of work" rule; noted in the T1.3 hand-off.
  - Safari and http dev, Identity's own clock, and `UpdatedAt` noise on users are already under "Watch out for".
  - Ordering `UserConfiguration` first stays: `ForeignKeyNames_NameTheirTables` catches any FK name it misses.

## Hand-offs to T1.3 (add to its scope in mvp.md)

- **Login:** `FindByEmailAsync`, then `PasswordSignInAsync(user, …, lockoutOnFailure: true)`. Without
  `lockoutOnFailure` the T1.2 lockout settings do nothing. The `User` overload is needed because the username is the
  id (D4). An unknown email answers like a wrong password.
- **The signup unit of work.**
  - `UserManager.CreateAsync` saves the **whole** context and dispatches its events. Tracked organization-owned rows
    would go with it, before any organization context exists, and the ownership interceptor throws.
  - So signup runs in one explicit transaction:
    1. create the user
    2. add the organization, then save
    3. open the trusted organization scope
    4. add the membership, then save
    5. commit
  - Post-commit events already wait for the commit (`DomainEventsTransactionInterceptor`).
- **Ordering gap in mvp.md:** T1.3's signup creates a membership, but the "trusted org scope for signup" is in T1.5's
  scope. Move that piece into T1.3, or pull it forward, when T1.3 is planned.
- **Unique-violation mapping:** `23505` on `ix_users_normalized_email` → 422 on `email`; on `ix_organizations_slug`
  → 422 on `slug`.

## Watch out for

- **Order in `OnModelCreating`.** If the configurations run before `base.OnModelCreating`, Identity's mapping
  overwrites the table and index names.
- **The keys volume takes its owner from the image** only when the volume is new. An `api-data-protection` volume
  created before the Dockerfile's `mkdir`/`chown` would be owned by root, and the non-root app couldn't write keys.
  `docker volume rm fixflow_api-data-protection` fixes it, and signs everyone out once.
- **Several hosts need another key store** (P24). A named volume lives on one Docker host; see D3's history for the
  way to B.
- **Secure cookie in Vite dev** (http://localhost:5173): Chrome and Firefox accept `Secure` cookies on localhost;
  Safari doesn't. Develop in Chromium or Firefox, and check it again in T1.3/T1.7. Tests already use an https
  `BaseAddress`.
- **Role changes don't stamp the membership's `UpdatedAt`.** Only the owned rows change, and the owner stays
  `Unchanged`. T1.5's membership events and T9.2's audit log cover role changes; don't patch the interceptor for it.
- **Lockout uses Identity's own clock**, not `IClock` (framework code, so CLAUDE.md §3.4 isn't broken). Tests can't
  move it with `FakeClock`, so lockout *expiry* goes untested. Starting the lockout is tested.
- **The Identity side tables** (claims, logins, tokens) stay empty in MVP, but `UserStore` needs them. Tokens will
  hold MFA data in Phase 2.
