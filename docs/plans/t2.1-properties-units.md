# T2.1 Property & unit domain + persistence — Implementation plan

**Status:** done 2026-11-03 (review pending) · **Size:** M (≈ 2 sessions) · **Branch:** `feat/t2.1-properties-units` from `dev`
**Scope and DoD:** `docs/plans/mvp.md` T2.1. This file only says how. Tick T2.1 there when done.

## Context

M2 starts here. T2.2 (endpoints) and T2.3 (UI) need the first business aggregates: `Property` (a building, with an
address and the IANA time zone that later drives SLAs and due dates, §11) and `Unit` (an apartment or space in it).
T2.1 adds only the domain, the mapping, the migration and their tests. No endpoints, so no OpenAPI or `gen:api` change.

## Decisions

**Confirmed with the user (2026-11-03):**
- **Address** = `Line1` (required), `Line2` (optional), `City` (required), `PostalCode` (optional, since some
  countries have none), `CountryCode` (required, ISO 3166 alpha-2, checked against the countries NodaTime's zone.tab
  knows: Domain may reference only NodaTime, and `RegionInfo` depends on ICU/invariant mode).
- **Unit names ignore case** ("4B" = "4b"). They're stored as typed, and a nondeterministic ICU collation on the
  column makes the partial unique index case-insensitive. The domain needs no normalized column.

**Settled by existing rules:**
- **Time zone rule:** accept a tzdb id, alias or canonical, matched exactly (case-sensitive), whose canonical zone is
  a *place* (in `TzdbDateTimeZoneSource.Default.ZoneLocations` ∪ `Zone1970Locations`). Store it as written, without
  canonicalizing (no build would turn `Europe/Oslo` into `Europe/Berlin`).
  - Why not `Tzdb.GetZoneOrNull`: it accepts `UTC+02:00` (NodaTime's fixed-offset ids), which fails the DoD.
    `Tzdb.Ids` alone still accepts `UTC` and `Etc/GMT-2`, which are fixed offsets too (§11: "never fixed offsets").
  - Aliases are accepted because browsers' `Intl.supportedValuesOf('timeZone')` (T2.3's autocomplete) may return
    `Europe/Kiev` or `Asia/Calcutta`. Tzdb never deletes ids, so a stored id stays valid after NodaTime updates.
- `Property` and `Unit` are **separate aggregates** (`Unit.PropertyId`, no navigations, as memberships do it):
  requests and tenant links reference units directly, and uniqueness is the database's job (P21/P27).
- Both: `AggregateRoot, IOrganizationOwned, ISoftDeletable, IAuditable`. **No `IHasRowVersion`** (§10 limits xmin to WO/MR).
- Soft delete = `Archive(Instant at)`. Archiving twice → `DomainException`, as `Suspend` does.
- **No update methods and no domain events yet.** T2.2 adds `Update(...)` along with its endpoint. Nothing consumes
  events yet (T9.2's audit log can add them).
- Plain FK `Unit → Property`. The interceptor plus T2.2's `VisibleTo` load already stop cross-org references; a
  composite `(organization_id, property_id)` FK would be a new pattern, so it's not added.
- The address is personal data (S24): `Address` prints no fields (`PrintMembers => false`, as the commands do).
- `Organization` stays as it is. The new text checks share one small Domain helper instead of copying
  `Organization.ValidName` five times.

  `using Unit = FixFlow.Domain.Properties.Unit;`.
- T2.2 decides what archiving a property does to its units (refuse while units are active, or archive them too).
- T2.2's validators reuse `PropertyTimeZone.IsValid` and `Address.IsValidCountryCode` (→ 400 field errors), and its
  handlers map `UniqueIndexes.UnitName` to a 422 field error (P27).
